## 一、架构设计相关

### Q1：为什么选择 Clean Architecture？三层各自的职责是什么？

**考察方向：** 架构理解能力、分层设计思想

**参考答案：**

选择 Clean Architecture 主要有三个原因：
1. **职责分离**：业务逻辑和 UI、数据源解耦，任何一层的变化不会影响其他层
2. **可测试性**：domain 层是纯 Dart 代码，不依赖任何 Flutter 框架，单元测试很容易写
3. **可维护性**：新人接手项目，能快速定位代码位置，找数据层的问题去 data，找业务逻辑去 domain

三层职责：
- **Presentation 层**：UI + 状态管理（Bloc）。只负责展示数据和接收用户交互，不包含任何业务逻辑
- **Domain 层**：业务逻辑核心。包含实体（Entity）、用例（UseCase）、仓库抽象（Repository 接口）。这一层不依赖任何外部框架，纯业务逻辑
- **Data 层**：数据的获取和持久化。包含数据源（DataSource：remote/local）、仓库实现（RepositoryImpl）、数据模型（Model）。负责把外部数据转换成 domain 层的 Entity

核心思想是**依赖倒置原则**：上层依赖抽象，不依赖具体实现。domain 层定义 Repository 接口，data 层去实现它，presentation 层通过 UseCase 调用。

### Q2：全局单例 Bloc 和页面级工厂 Bloc 怎么选？依据是什么？

**考察方向：** 状态管理选型能力、对生命周期的理解

**参考答案：**

我主要根据**状态的共享范围**来决定：

**全局单例 Bloc（registerLazySingleton）**：
- 适用场景：需要跨页面共享状态、多个地方同时读写
- 项目中的例子：
  - `CartBloc`：购物车数据在商品详情页加购、首页角标、购物车页面都要用到，必须全局共享
  - `AuthBloc`：登录态是全局的，路由守卫、各个页面的权限判断都依赖
  - `HomeBloc` / `CategoryBloc`：底部 Tab 切换时不希望重建，避免重复请求和滚动位置丢失

**页面级工厂 Bloc（registerFactory）**：
- 适用场景：页面独立状态，进入页面创建，退出页面销毁
- 项目中的例子：
  - `ProductDetailBloc`：每个商品详情页都是独立的，进入新的商品页面需要新的实例
  - `SearchBloc`：每次进入搜索页是独立的搜索状态
  - `OrderListBloc` / `OrderDetailBloc`：订单页面状态独立，不需要跨页面共享

**选型依据总结：**
1. 是否需要跨页面共享？→ 需要就单例
2. Tab 切换是否需要保留状态？→ 需要就单例
3. 是否进入新页面就是全新状态？→ 是就工厂

用 get_it 注册而不是用 `BlocProvider` 全局包裹的原因是：Bloc 的创建和销毁更灵活，而且不依赖 context，在任何地方都能获取。

### Q3：get_it 和 Provider / Riverpod 有什么区别？为什么用 get_it？

**考察方向：** 依赖注入理解、技术选型能力

**参考答案：**

它们解决的问题不太一样：

- **Provider / Riverpod**：本质是「状态管理 + 依赖注入」的结合体，基于 InheritedWidget，和 Widget 树深度绑定，适合管理 UI 相关的状态
- **get_it**：是纯粹的「服务定位器」（Service Locator），不依赖 context，不依赖 Flutter 框架，可以在任何地方使用

**为什么我们项目用 get_it？**

1. **和 Clean Architecture 更搭**：domain 层是纯 Dart 的，不应该依赖 Flutter 的 context，get_it 可以在纯 Dart 代码里直接用
2. **全局 Bloc 更方便**：购物车、认证这种全局单例 Bloc，用 get_it 注册后，在任何页面、任何工具类里都能 `getIt<CartBloc>()` 获取，不需要传 context
3. **生命周期控制灵活**：单例（Singleton）、懒加载单例（LazySingleton）、工厂（Factory）三种模式都支持，可以精确控制每个对象的生命周期
4. **和 flutter_bloc 配合很好**：页面里用 `BlocProvider.value(value: getIt<HomeBloc>())` 来提供 Bloc，既利用了 get_it 的注入能力，又享受了 BlocProvider 的上下文查找

当然 get_it 也有缺点：它不是编译期安全的，如果类型注册错了运行时才会报错。Riverpod 在这方面更好。但综合来看，对于我们这种 Clean Architecture + 全局状态较多的项目，get_it 更合适。

## 二、混合开发相关（重点，Android 背景加分项）

### Q4：Flutter 混合开发有哪些集成方式？你们为什么选多仓 + Flutter Module？

**考察方向：** 混合开发方案选型、工程化能力

**参考答案：**

主要有三种集成方式：

1. **单仓源码集成**：Flutter 代码和原生代码放在同一个仓库里，原生通过源码依赖 Flutter 模块
   - 优点：联调方便，改了 Flutter 代码原生直接生效
   - 缺点：原生团队必须搭 Flutter 环境，耦合度高，发版节奏绑定

2. **多仓 + 产物集成（Flutter Module）**：Flutter 是独立仓库，打成 aar / framework 产物，原生通过 maven 依赖
   - 优点：团队解耦，原生不需要 Flutter 环境，版本独立，发版节奏各自控制
   - 缺点：联调麻烦一点，需要打产物或本地源码依赖切换

3. **FlutterView 嵌入**：把 Flutter 页面作为一个 View 嵌入原生页面的局部区域
   - 优点：灵活，可以原生和 Flutter 混在同一个页面
   - 缺点：实现复杂，生命周期管理麻烦

**我们选多仓 + Flutter Module 的原因：**

1. **团队规模和分工**：原生团队和 Flutter 团队是两个独立的团队，各有各的迭代节奏，多仓更符合协作模式
2. **原生团队体验**：Android 和 iOS 同事不需要搭 Flutter 环境，正常拉代码、同步 gradle 就能编译，不影响他们的开发体验
3. **版本管理清晰**：Flutter 模块有自己的版本号，原生按需升级，出了问题可以快速回滚版本
4. **多端复用**：同一个 Flutter module 可以同时给 Android 和 iOS 两边用，产出一致

当然联调的时候会稍微麻烦一点，我们的做法是：开发阶段用**本地源码依赖**（`include_flutter.groovy`），方便调试；正式发版用 **aar 产物**，通过 maven 管理。

### Q5：FlutterEngine 预热你们是怎么做的？时机怎么选？

**考察方向：** 性能优化、引擎管理深度

**参考答案：**

我们用的是 `FlutterEngineCache` 来做引擎缓存，核心逻辑在 `FlutterBridgeManager` 里：

**具体实现：**
1. 定义一个全局的 engineId，比如 `"ecom_engine"`
2. 预加载时创建 `FlutterEngine` 实例，执行 `DartExecutor` 的入口函数（也就是 `main()`）
3. 把引擎实例放到 `FlutterEngineCache` 里缓存
4. 打开 Flutter 页面时，从 cache 里取已经预热好的引擎，不用重新创建

**预热时机的选择**是一个权衡问题，我们考虑了几种方案：

| 方案 | 优点 | 缺点 |
|------|------|------|
| Application.onCreate 就预热 | 打开 Flutter 页面最快 | 拖慢 App 启动速度，占用内存 |
| 首页渲染完成后异步预热 | 不影响启动速度，大部分场景够用 | 进入首页后立刻点 Flutter 入口可能还没预热完 |
| 用户点击入口前预判 | 最省资源 | 预判不准，实现复杂 |

我们最终选的是**首页渲染完成后异步预热**，在 `MainActivity` 的 `onPostResume` 里调 `preloadEngine()`。因为电商 App 里 Flutter 页面（电商模块）的入口大多在首页，用户从启动到点击入口至少有几秒时间，引擎足够预热完。平衡了启动速度和 Flutter 页面的打开速度。

**效果：** 预热后打开 Flutter 页面基本上是秒开（<100ms），首次冷启动创建引擎的话大概需要 500~800ms，提升很明显。

**补充：多引擎 vs 共享引擎**
- 我们用的是**共享单引擎**模式，所有 Flutter 页面共享同一个引擎和 Dart isolate
- 好处是内存占用小，状态天然共享（比如购物车数据不用跨引擎同步）
- 缺点是不同 Flutter 页面的路由栈在同一个 isolate 里，需要混合栈管理
- 一般电商 App 用共享引擎足够了，只有特殊场景（比如独立的 Flutter 浮窗、需要完全隔离的业务）才用多引擎

### Q6：MethodChannel 你们是怎么封装的？为什么这么设计？

**考察方向：** 平台通道理解、封装设计能力

**参考答案：**

我们封装了一个 `NativeBridge` 单例管理器，业务层不直接和 MethodChannel 打交道，都通过这个管理器来调用原生能力。

**设计思路：**

1. **Channel 名统一管理**：用常量类 `BridgeChannels` 统一定义所有 Channel 名字，命名规则是「包名 + 功能名」，比如 `com.example.flutter_ecom/native_bridge`，避免和其他插件的 Channel 冲突。原生那边也是同样的常量，两边对齐

2. **单例模式**：`NativeBridge` 是单例，全局共享一个 MethodChannel 实例，避免重复创建

3. **统一异常处理**：每个方法调用都用 try-catch 包了 `PlatformException`，统一打日志，失败时返回 null 或默认值，业务层不用处理异常

4. **集中管理所有原生方法**：`BridgeMethods` 常量类定义了所有方法名，一共十几个：
   - 通用：getAppInfo、getDeviceInfo、toast、navigateBack
   - 登录：nativeLogin、getToken、logout
   - 支付：weChatPay（微信支付）
   - 相机：takePhoto、pickImage
   - 推送：getPushToken

**为什么不用插件的形式？**
- 因为这些 Bridge 是和业务强相关的，不是通用能力
- 集中放在一个文件里，和原生同学对齐协议的时候更方便，一个文件就能看完所有接口
- 插件适合通用能力（camera、shared_preferences 这种），业务 Bridge 不需要抽插件

**和原生的协作流程：**
- 先由 Flutter 侧定义好 Channel 名、方法名、参数结构（相当于接口协议）
- 原生（Android/iOS）两边分别实现这个协议
- Flutter 侧调用，原生侧返回结果，两边用同一套常量定义，避免手写出错

### Q7：混合开发中登录态是怎么共享的？

**考察方向：** 实际项目经验、问题解决能力

**参考答案：**

我们的方案是**原生维护登录态，Flutter 侧缓存 + Channel 兜底**。

**具体策略：**

1. **登录操作在原生完成**：用户登录走的是原生的登录页，登录成功后 Token 存在原生的 SharedPreferences 里

2. **Flutter 启动时同步 Token**：Flutter 引擎初始化后，通过 MethodChannel 调用 `getToken` 方法，从原生获取 Token，存在 Flutter 自己的 SharedPreferences 里

3. **请求时用本地缓存的 Token**：Dio 的 AuthInterceptor 优先读 Flutter 本地的 Token，加到请求头里

4. **Token 失效时的处理**：收到 401 时，Flutter 侧通过 Channel 通知原生跳登录页，登录成功后原生再把新 Token 同步给 Flutter

**为什么这么设计？**
- 登录态是 App 全局的，不止 Flutter 模块用，原生页面也用，统一由原生管理最合理
- Flutter 侧缓存一份是为了性能，不用每次发请求都走 Channel（Channel 是异步的，而且有开销）
- 登录登出这些状态变化，都通过 Channel 通知 Flutter 侧同步，保证两端一致

**Dio 拦截器同步 Token 的坑：**
Dio 的 `onRequest` 拦截器是同步的，如果本地没有 Token 想通过 Channel 去原生取，是没法直接 await 的。我们的做法是在 App 启动时就把 Token 从原生同步到 Flutter 本地，拦截器直接读本地，避开了这个问题。

### Q7.5：闪屏页（Splash Screen）用原生实现还是 Flutter 实现？为什么？

**考察方向：** 混合开发经验、对 App 启动流程的理解

**参考答案：**

**闪屏页必须用原生实现，这是行业标准做法。** 原因很简单：

**1. 冷启动时 Flutter 引擎还没初始化**

App 冷启动的流程是：点击图标 → Application 初始化 → 首屏 Activity 启动 → FlutterEngine 创建 → Dart 代码执行 → Flutter 渲染第一帧。在 FlutterEngine 创建好、第一帧渲染出来之前，屏幕上必须有东西显示，不然就是白屏/黑屏。这个阶段 Flutter 自己还没"醒"，根本不可能用 Flutter 画闪屏页。

**2. 原生闪屏是系统级的，性能最好**

Android 上用 `windowBackground` 或者 Android 12+ 的 `SplashScreen` API，iOS 上用 `LaunchScreen.storyboard`，都是系统层面直接渲染的，完全不占主线程时间，用户点图标立刻就能看到。

**3. 混合开发场景下闪屏是整个 App 的入口**

我们这个项目是混合开发，电商模块是 Flutter 的，但整个 App 的入口是原生的。闪屏页是给整个 App 用的，跟 Flutter 没关系。用户从原生首页点击电商入口的时候，FlutterEngine 已经在后台预热好了，Flutter 页面是秒开的，所以 Flutter 侧根本不需要单独的闪屏页。

**补充：纯 Flutter App 呢？**

纯 Flutter App 也是一样的——启动页必须原生做。但 Flutter 端可以再加一个"初始化加载页"，就是 Flutter 第一帧渲染出来之后，数据还在初始化（比如拉配置、检查登录态、初始化 SDK）的时候展示的页面。那个页面是 Flutter 内部的，不是用来替代原生冷启动白屏的，两个层级不一样。

**一句话总结：闪屏页是 App 启动的第一张脸，得原生打底，Flutter 还没睡醒呢。**

### Q7.6：混合开发中 Flutter 页面打开后状态栏颜色不对（蓝色/紫色）是什么原因？怎么解决？

**考察方向：** 混合开发踩坑经验、对 Android 主题系统的理解、问题排查能力

**参考答案：**

这个问题是 Flutter 混合开发中非常典型的一个坑，我在项目中也遇到过。

**现象：**
- 直接运行 Flutter Module（纯 Flutter 模式），状态栏颜色正常（由 Flutter 的 AppBar / AnnotatedRegion 控制）
- 运行 Android 壳工程打开 Flutter 页面，状态栏变成了壳工程主题的 primaryColor（紫色/蓝色）

**根本原因：**

FlutterActivity 没有单独指定主题，继承了 `application` 标签上的主题。壳工程的默认主题有自己的 `colorPrimary`（比如 `#FF6200EE` 紫色），所以状态栏就是紫色的。

而纯 Flutter App 中，Flutter 生成的 Android 工程里 FlutterActivity 有自己的主题（`LaunchTheme` / `NormalTheme`），状态栏是透明的，Flutter 能自己控制。

**解决方案：**

给 FlutterActivity 单独设置一个透明状态栏的主题，让 Flutter 自己控制状态栏颜色。三步：

**第一步：在 `themes.xml` 中定义 Flutter 专用主题**

```xml
<style name="Theme.Flutter" parent="Theme.MaterialComponents.DayNight.NoActionBar">
    <!-- 状态栏透明，让 Flutter 页面自己控制 -->
    <item name="android:statusBarColor">@android:color/transparent</item>
    <!-- 状态栏图标颜色，根据 App 设计风格设置 -->
    <item name="android:windowLightStatusBar">false</item>
    <!-- 去掉 ActionBar -->
    <item name="windowActionBar">false</item>
    <item name="windowNoTitle">true</item>
    <!-- 页面背景白色，和 Flutter 默认背景一致 -->
    <item name="android:windowBackground">@color/white</item>
</style>
```

**第二步：在 `AndroidManifest.xml` 中给 FlutterActivity 指定主题**

```xml
<activity
    android:name="io.flutter.embedding.android.FlutterActivity"
    android:theme="@style/Theme.Flutter"
    ... />
```

**第三步：Flutter 侧正常使用 AppBar / AnnotatedRegion 控制状态栏**

设置完之后，Flutter 侧的 `AppBar`、`AnnotatedRegion<SystemUiOverlayStyle>` 就能完全控制状态栏的颜色和图标明暗，和纯 Flutter App 的效果完全一致。

**扩展思考：为什么会有这个差异？**

纯 Flutter App 的 Android 工程是 `flutter create` 自动生成的，它的 `AndroidManifest.xml` 里 FlutterActivity 已经配好了 `NormalTheme` 和 `LaunchTheme`。但在混合开发中，我们是自己在壳工程的 manifest 里注册 FlutterActivity，很容易漏掉主题配置，导致继承 application 的主题，出现"蓝色状态栏"的问题。

**一句话总结：混合开发中 FlutterActivity 必须单独配主题，不能让它继承 application 的主题，不然状态栏就是壳工程的颜色。**

## 三、网络层与错误处理

### Q8：你们的拦截器链是怎么设计的？为什么是这个顺序？

**考察方向：** 网络层设计深度、细节理解

**参考答案：**

我们基于 Dio 设计了三层拦截器，顺序是：`AuthInterceptor → LoggingInterceptor → ErrorInterceptor`。

**各自职责：**

1. **AuthInterceptor**：负责往请求头里加 `Authorization: Bearer <token>`，以及 401 的全局处理（触发登出）
2. **LoggingInterceptor**：负责打印请求和响应的完整日志（URL、方法、头、body、状态码、响应体），便于调试
3. **ErrorInterceptor**：负责统一记录错误日志，把错误信息上报（项目里预留了埋点位置）

**为什么是这个顺序？**

Dio 的拦截器有个特点：
- **请求阶段（onRequest）**：按添加顺序执行
- **响应/错误阶段（onResponse / onError）**：按添加的**逆序**执行

所以顺序很重要：

1. **Auth 放最前面**：这样 LoggingInterceptor 能记录到加完 Token 之后的完整请求头，调试的时候能看到 token 有没有加上
2. **Logging 放中间**：请求日志在 Auth 之后、Error 之前，响应日志先经过 Logging 再到 Error
3. **Error 放最后面**：这样错误回来的时候最先被 ErrorInterceptor 捕获（因为逆序），可以最早做统一错误处理

如果顺序反过来，比如 Logging 放最前面，那打印出来的请求头是没有 Token 的，调试的时候就不方便了。

### Q9：为什么用 dartz 的 Either 做错误处理？和 try-catch 比有什么好处？

**考察方向：** 函数式编程理解、错误处理设计

**参考答案：**

我们用 `dartz` 的 `Either<Failure, T>` 来处理错误，核心思想是**把错误变成返回值的一部分**，而不是用异常抛出。

**定义了 6 种 Failure 类型：**
- `ServerFailure`：服务器错误（5xx）
- `NetworkFailure`：网络连接失败
- `UnauthorizedFailure`：未授权（401）
- `BusinessFailure`：业务逻辑错误（code != 200）
- `CacheFailure`：缓存读写失败
- `UnknownFailure`：未知错误

用类型别名简化写法：`typedef Result<T> = Either<Failure, T>;`

**和 try-catch 比的好处：**

1. **编译期强制处理失败**：函数返回 `Either<Failure, T>`，调用方必须处理左值（失败）和右值（成功），不会像 try-catch 那样忘记 catch 导致未捕获异常
2. **错误类型明确**：一看函数签名就知道可能返回哪些错误，不用翻文档或看 throw 的地方
3. **函数式编程风格**：可以用 `fold`、`map`、`flatMap` 等操作符链式处理，代码更流畅
4. **和 Clean Architecture 很搭**：domain 层定义 Failure，data 层负责把各种异常转换成 Failure，presentation 层根据不同 Failure 做不同 UI 展示

**项目中的实际用法：**

```dart
// Repository 层：把异常转成 Either
@override
Future<Result<UserEntity>> login({required phone, required password}) async {
  try {
    final user = await _remoteDataSource.login(phone: phone, password: password);
    return Right(user.toEntity());
  } catch (e) {
    return Left(ErrorHandler.handleError(e));
  }
}

// Bloc 层：用 fold 处理两种结果
final result = await _loginUseCase.call(phone: phone, password: password);
result.fold(
  (failure) => emit(LoginFailure(failure.message)),
  (user) => emit(LoginSuccess(user)),
);
```

当然也不是所有场景都适合 Either，比如一些纯 UI 层的异常处理，用 try-catch 更直接。核心业务逻辑用 Either，能让代码更健壮。

## 四、路由与状态管理

### Q10：go_router 怎么实现登录态联动的路由守卫？

**考察方向：** 路由深度、状态联动

**参考答案：**

go_router 本身支持 `redirect` 参数做路由守卫，但有个问题：**redirect 只在路由跳转时触发一次**，如果登录态在页面停留期间发生变化（比如 token 过期了），路由不会自动重新评估。

我们的解决方案是用 `refreshListenable` + 自定义 `ChangeNotifier`：

**实现步骤：**

1. 定义一个 `_AuthStateListenable` 继承 `ChangeNotifier`
2. 在它的构造函数里监听 `AuthBloc.stream`，每当 Auth 状态变化时调用 `notifyListeners()`
3. 把这个 Listenable 传给 `GoRouter` 的 `refreshListenable` 参数
4. 当 `notifyListeners()` 被调用时，go_router 会重新执行 `redirect` 回调，根据最新的登录态决定是否重定向

**关键代码逻辑：**

```dart
class _AuthStateListenable extends ChangeNotifier {
  _AuthStateListenable() {
    _authSubscription = getIt<AuthBloc>().stream.listen((_) {
      notifyListeners();
    });
  }
  late final StreamSubscription<AuthState> _authSubscription;
}

// 路由配置
GoRouter(
  refreshListenable: _AuthStateListenable(),
  redirect: (context, state) {
    final isLoggedIn = getIt<AuthBloc>().state.status == AuthStatus.authenticated;
    if (!isLoggedIn && state.location.startsWith('/profile')) {
      return '/login';
    }
    return null;
  },
)
```

**为什么不用直接在 bloc 里跳转？**
- 路由守卫是声明式的，统一在一个地方管理所有权限判断，比每个页面自己判断更清晰
- 用 refreshListenable 的方式，登录态一变，所有受保护的路由都会自动重新评估，不会遗漏
- 符合 go_router 的设计哲学：路由状态由应用状态驱动

## 五、本地存储

### Q11：为什么购物车用 Hive 不用 SharedPreferences？Hive 和 SQLite 比呢？

**考察方向：** 技术选型能力、存储方案对比

**参考答案：**

**为什么不用 SharedPreferences 存购物车？**

1. **结构不合适**：SharedPreferences 是 KV 存储，value 只能是基本类型和字符串。购物车是列表结构，存 SP 要手动转 JSON 字符串，读出来还要解析，很麻烦
2. **性能不行**：SP 是 XML 文件存储，读写频繁的话性能差，而且 SP 的 apply 是异步的，可能丢数据
3. **增删改查不方便**：加一个商品、改数量、删除一个，都要把整个列表读出来、改、再存回去

**为什么用 Hive 不用 SQLite（sqflite）？**

| 维度 | Hive | SQLite (sqflite) |
|------|------|-----------------|
| 数据模型 | NoSQL，对象存储，直接存 Dart 对象 | 关系型，需要建表、写 SQL |
| 性能 | 纯 Dart 实现，直接读写内存映射文件，很快 | 要通过 MethodChannel 走原生 SQLite，有通道开销 |
| 开发效率 | 加个 TypeAdapter 就能用，非常快 | 需要写表结构、SQL 语句、ORM 映射 |
| 查询能力 | 只能按 key 查，没有复杂查询 | 支持 SQL 复杂查询、联表、聚合 |
| 类型安全 | TypeAdapter 保证类型安全 | 需要自己做对象映射 |

购物车这种场景，数据结构简单（就是商品列表），没有复杂查询需求，用 Hive 最合适：开发快、性能好、代码简洁。

如果是有复杂查询需求的场景（比如订单列表要按状态、时间、金额多条件筛选），那 SQLite 更合适。

**我们的选型原则：**
- 轻量 KV（Token、配置、标记）→ SharedPreferences
- 结构化对象列表、简单 CRUD → Hive
- 复杂查询、关系型数据 → SQLite

## 六、性能优化

### Q12：你们做了哪些 Flutter 性能优化？

**考察方向：** 性能优化经验、问题解决能力

**参考答案：**

主要做了以下几个方面的优化：

**1. 列表性能优化**
- 所有长列表都用 `ListView.builder` 而不是 `ListView(children: [])`，按需构建 item
- 商品列表项的 Widget 尽可能用 `const` 构造函数，避免不必要的重建
- 用 `BlocSelector` 替代 `BlocBuilder`，只监听需要的状态字段，减少刷新范围
- 图片用 `cached_network_image`，内存 + 磁盘两级缓存，避免重复下载和解码

**2. 混合开发性能优化**
- FlutterEngine 预加载：首页渲染完成后异步预热引擎，Flutter 页面打开耗时从 800ms 降到 100ms 以内
- 共享单引擎模式：所有 Flutter 页面共享一个引擎，减少内存占用

**3. 交互优化**
- 搜索框输入做了 500ms 防抖，避免每次按键都发请求，减少服务端压力也减少 UI 刷新
- 按钮防重复点击：用节流或者状态控制，防止用户快速点击多次触发重复请求

**4. 图片优化**
- 统一封装 `AppNetworkImage` 组件，统一占位图、错误图、缓存策略
- 列表里的图片用指定的宽高，避免图片加载后导致列表项高度变化引起的整体跳动

**5. 状态管理优化**
- 全局单例 Bloc 和页面级工厂 Bloc 合理分配，避免全局状态过多导致不必要的通知
- Bloc 的 state 用 Equatable 值比较，相同 state 不触发重建

**优化效果：** 核心页面（首页、商品列表）滚动帧率稳定在 55fps 以上，中低端机上也比较流畅。

如果要继续深入优化，还可以做：分帧加载（把一帧的工作拆分到多帧）、图片预缓存（提前缓存即将出现在视口的图片）、列表项的 `AutomaticKeepAliveClientMixin` 保活等。

### Q12.5：BlocSelector 细粒度刷新是什么？你具体在哪些地方用了？

**考察方向：** 性能优化细节、对 flutter_bloc 的深度理解、是否真的做过

**参考答案：**

**BlocSelector 是什么？**

`BlocBuilder` 的问题是：state 里任何一个字段变了，整个 builder 都会重建。但很多时候，UI 组件只关心 state 中的某一个或某几个字段，其他字段变化跟它没关系——重建就是浪费。

`BlocSelector` 就是解决这个问题的：它让你通过 `selector` 函数只取出 state 中你关心的那一部分，只有当这部分值真的变了的时候，才会触发 builder 重建。原理上就是内部做了个 `distinctUntilChanged` 的效果。

类比 Android 的话，相当于 Flow 的 `map { state -> state.field }.distinctUntilChanged().collect { ... }`。

---

**我们项目中用了三个地方：**

**1. 底部导航栏的购物车角标**
- 位置：`lib/core/router/app_router.dart` 的 `MainShell`
- 问题：底部导航是全局组件，如果用 `BlocBuilder` 监听整个 `CartState`，用户在购物车页切换选中状态、改商品数量，底部导航都会跟着重建——但角标只显示 `totalCount`，其他字段变化跟它没关系
- 改造：`BlocSelector<CartBloc, CartState, int>`，selector 返回 `state.totalCount`
- 效果：只有购物车总数变化时，角标才刷新

**2. 商品详情页底部栏的购物车徽标**
- 位置：`lib/features/product_detail/presentation/widgets/product_bottom_bar.dart`
- 问题：商品详情页用户可能频繁操作（加购、选规格），购物车 state 变化很频繁，但徽标只显示数量
- 改造：同样只监听 `totalCount`
- 效果：减少商品详情页交互时的不必要重建

**3. 购物车页面的底部合计栏**
- 位置：`lib/features/cart/presentation/pages/cart_page.dart` 的 `bottomNavigationBar`
- 问题：底部栏需要 `isEmpty`、`isAllSelected`、`selectedCount`、`selectedTotalPrice` 这几个值，但不需要知道商品列表的具体内容（比如哪个商品改了名字、换了图片）。如果用 `BlocBuilder`，列表里任何商品变化都会触发底部栏重建
- 改造：我专门抽了一个 `CartBottomBarState` 类（继承 Equatable），把底部栏需要的字段封装进去，selector 返回 `CartBottomBarState.fromCartState(state)`
- 效果：商品列表内容变化（如图片加载完成、单个商品属性变化）不会触发底部栏重建，只有选中状态、总价、数量这些底部栏关心的字段变了才重建

---

**为什么不每个组件都用 BlocSelector？**

也不是所有地方都要用，有个权衡：
- **列表整体区域** → 用 `BlocBuilder`，因为列表内容跟整个 state 都相关
- **独立的小组件**（如角标、按钮、底部栏）→ 用 `BlocSelector`，因为它只关心部分字段
- **只监听一个字段** → 直接 selector 返回基本类型（int / String / bool）
- **监听多个字段** → 封装一个小的 state 片段类，继承 Equatable，确保值比较正确

过度使用 BlocSelector 会增加代码复杂度，该用 BlocBuilder 的地方还是用，只在**明确知道某些字段变化不需要重建**的地方用 BlocSelector，收益最大。

### Q12.6：遇到过 `BoxConstraints forces an infinite width` 的布局错误吗？怎么排查的？

**考察方向：** 布局调试能力、问题排查思路、对 Flutter 布局原理的理解

**参考答案：**

遇到过，在做订单详情页底部操作栏的时候踩过这个坑。

**现象：**
- 订单详情页底部操作栏（Scaffold.bottomNavigationBar）里有 `Row` 包着几个按钮
- 待发货状态的订单详情正常，其他状态报错 `BoxConstraints forces an infinite width`
- 页面整体空白，控制台报一串 `RenderBox was not laid out`

**根本原因：**

`Scaffold` 的 `bottomNavigationBar` 参数接收的是一个普通 `Widget`，但它内部的布局约束在某些情况下可能会传下无限宽度。特别是当 `bottomNavigationBar` 的 child 是 `BlocBuilder` 这类**没有 intrinsic width**的组件时，Flutter 在布局时可能会给子组件传递 `infinite` 的宽度约束。

按钮（ElevatedButton/OutlinedButton）内部的 `RenderConstrainedBox` 收到无限宽度约束后，无法确定自己的宽度，就抛出 `BoxConstraints forces an infinite width`。

**为什么待发货状态正常？**

待发货状态的底部是两个 `OutlinedButton`，它们的样式计算在无限约束下可能刚好能算出宽度（比如边框的存在影响了布局计算），而 `ElevatedButton` 的样式在某些 Flutter 版本下对无限宽度约束更敏感。所以表现为"有的状态正常，有的状态报错"——看起来很诡异，其实都是同一个根因。

**解决方案：**

给 `bottomNavigationBar` 的内容包一层明确宽度约束的组件，比如 `SizedBox(width: double.infinity)`：

```dart
bottomNavigationBar: BlocBuilder<OrderDetailBloc, OrderDetailState>(
  builder: (context, state) {
    final content = ...; // 底部栏内容
    // 明确告诉框架底部栏宽度等于屏幕宽度
    return SizedBox(width: double.infinity, child: content);
  },
),
```

原理很简单：`SizedBox(width: double.infinity)` 会把父级的无限宽度约束**转换成紧约束**（宽度 = 可用最大宽度），然后传给子组件。子组件（Row、按钮）收到有界的宽度约束，就能正常布局了。

**排查思路总结：**

1. 先看错误堆栈的第一行，定位是哪个 widget 报错（`ElevatedButton at line 637`）
2. 往上找父级，看是谁给它传了无限宽度约束
3. 在合适的层级加宽度约束（SizedBox、Container、Expanded 等）
4. 对比"正常"和"异常"的差异，反推根因（正常 vs 异常的差异往往指向问题本质）

**一句话总结：** 底部栏、AppBar 等 Scaffold 的槽位组件，记得在最外层给一个明确的宽度约束，避免无限宽度约束传递下去。

## 七、基础设施与工程化

### Q13：你们的 Mock 方案是怎么做的？有什么好处？

**考察方向：** 工程化能力、前后端协作

**参考答案：**

我们的 Mock 方案是**自定义 Dio 的 HttpClientAdapter**，核心是 `MockApiAdapter` 这个类。

**实现思路：**
1. 实现 `HttpClientAdapter` 接口，替换 Dio 默认的适配器
2. 根据请求的 URL 路径，从本地 asset 里读取对应的 Mock JSON 文件
3. 模拟网络延迟（300~800ms 随机），再返回数据
4. 上层业务代码完全感知不到 Mock 的存在

**切换方式：**
在 `service_locator.dart` 里有一行配置：
```dart
const bool useMock = true;
```
创建 DioClient 的时候，根据这个配置决定是否传入 MockApiAdapter。只改这一行，就能在 Mock 和真实环境之间切换。

**好处：**

1. **前后端并行开发**：后端接口还没好的时候，Flutter 侧可以先根据接口文档写 Mock 数据，并行开发，不阻塞进度
2. **对上层透明**：Repository 层、Bloc 层、UI 层的代码完全不用改，Mock 和真实接口的切换只在基础设施层
3. **便于调试各种状态**：可以方便地模拟网络延迟、请求失败、空数据等各种边界情况，测试页面的不同状态
4. **演示方便**：没有后端环境的时候也能完整演示 App 功能

**和其他 Mock 方案的对比：**
- Mock 后端服务（如 Mockoon）：需要起服务，换环境麻烦，适合联调阶段
- 前端 Mock 拦截器：侵入性强，每个接口都要写 Mock 代码
- 我们这种 HttpClientAdapter 方案：最轻量，对业务代码零侵入，适合开发阶段快速 Mock

## 八、开放性问题

### Q14：做这个项目遇到的最大的难点是什么？怎么解决的？

**考察方向：** 问题解决能力、项目深度

**参考答案（可以根据真实情况选一个说）：**

**难点一：混合开发的登录态同步问题**

刚接入的时候，登录态不同步是个很头疼的问题。用户在原生页登录了，进 Flutter 购物车还是未登录状态；在 Flutter 里退出了，回到原生页还是登录态。

**解决思路：**
1. 明确「原生是登录态的唯一持有者」，Flutter 不自己管理登录，只是同步一份缓存
2. 登录、登出操作都走原生，完成后通过 Channel 通知 Flutter 同步状态
3. Flutter 启动时第一时间从原生拉取 Token，存到本地
4. Dio 拦截器收到 401 时，通知原生跳登录页，不自己处理

最后效果是两端登录态完全一致，用户感知不到切换。

---

**难点二：Flutter 插件和原生 Android 的版本兼容性问题**

项目升级 Flutter 版本的时候遇到过插件兼容问题。比如 Flutter 新版本移除了 `flutter.compileSdkVersion` 这个扩展属性，但是 `shared_preferences_android` 这些插件的老版本还在用，导致原生编译失败。

**解决思路：**
1. 把有问题的插件 vendor 到项目的 `third_party/` 目录下
2. 手动修补它们的 `build.gradle` 文件，适配新的 Flutter 版本
3. 在 `pubspec.yaml` 里用 `dependency_overrides` 指向本地修补后的版本
4. 等上游插件发布兼容版本后，再切回去

这个问题涉及 Flutter、Gradle、插件三方的版本依赖关系，排查起来比较费时间，但解决之后对 Flutter 插件机制和 Gradle 构建的理解深入了很多。

---

### Q15：如果让你重新做这个项目，有什么可以改进的地方？

**考察方向：** 反思能力、技术视野

**参考答案：**

有几个方面可以做得更好：

1. **测试覆盖**：目前单元测试和 Widget 测试覆盖得比较少。应该给 UseCase 和 Repository 层补单元测试，核心页面补 Widget 测试，保证重构和迭代的质量

2. **代码生成**：目前 Hive 的 TypeAdapter、JSON 序列化都是手写的。可以用 `build_runner` + `json_serializable` + `hive_generator` 做代码生成，减少手写模板代码，也避免手写出错

3. **状态管理更精细**：一些页面的 Bloc 可以拆得更细，或者用 `Cubit` 替代 `Bloc`（对于简单状态的页面，Cubit 更轻量）。还可以考虑引入 `freezed` 来生成 state 的 union type，让状态判断更安全

4. **国际化支持**：目前只有中文，如果 App 要出海，需要从一开始就把 i18n 框架搭好，用 `flutter_localizations` + `intl` 做多语言

5. **性能监控埋点**：目前没有线上性能数据。应该加一些性能埋点，比如页面加载时间、列表滑动帧率、内存占用等，用数据驱动优化，而不是靠感觉

6. **组件库抽离**：通用组件如果多个项目复用，可以抽成独立的 UI 组件库 package，通过 pub 或 git 依赖
