# 面试指南：Flutter 混合开发集成方案

本文档系统整理 Flutter Module 嵌入原生 App 的两种集成方式、原理对比、以及面试标准答案。
面试前 10 分钟过一遍，回答更有条理。

---

## 一、核心问题（面试官必问）

> **Q：你们 Flutter 和原生是怎么集成的？**

这是混合开发面试的开门题，答得好不好直接影响面试官对你技术深度的判断。

---

## 二、两种集成方式

### 方式 A：源码依赖（Source Integration）

#### 配置

```kotlin
// settings.gradle.kts
apply(from = "../flutter_ecom/.android/include_flutter.groovy")

// app/build.gradle.kts
implementation(project(":flutter"))
```

#### 工作原理

```
原生 settings.gradle
      │
      ▼
include_flutter.groovy  ←────── Flutter 官方提供的脚本
      │
      ├─ 注册 :flutter 子项目 → .android/Flutter/ （自动生成的 Library 工程）
      │                          └── build.gradle 应用 Flutter Gradle 插件
      │
      └─ 注册所有 Flutter 插件子项目（:shared_preferences, :hive 等）

原生 app 通过 implementation(project(":flutter")) 依赖
      │
      ▼
编译时 Flutter Gradle 插件：
  1. 编译 Dart 代码 → AOT 产物（release）/ JIT （debug）
  2. 打包 Flutter 引擎 + Dart 产物 + 资源 → aar
  3. 原生 App 最终包含所有 Flutter 相关 so 和资源
```

#### 优缺点

| 维度 | 评价 |
|------|------|
| 开发效率 | ⭐⭐⭐⭐⭐ 改完立即生效，调试方便 |
| 编译速度 | ⭐⭐ 慢，每次都要编译 Dart |
| Flutter 环境要求 | 需要本地安装 Flutter SDK |
| 团队协作 | 耦合高，原生团队也需要 Flutter 环境 |
| 适用场景 | 开发调试阶段、Flutter 开发同学本地使用 |

---

### 方式 B：产物依赖（AAR / Framework）

#### 配置

```kotlin
// app/build.gradle.kts
// 从 maven 仓库依赖（多仓正式方案）
implementation("com.example.flutter_ecom:flutter_release:1.2.3")

// 或本地 aar 文件（临时调试）
implementation(files("libs/flutter-release.aar"))
```

#### 打 aar 命令

```bash
cd flutter_ecom

# 只打 release 包
flutter build aar --no-debug --no-profile

# 指定架构（减小包体积）
flutter build aar --no-debug --no-profile --target-platform android-arm64
```

#### 产物位置

```
flutter_ecom/build/host/outputs/repo/
└── com/example/flutter_ecom/
    ├── flutter_release/1.0/
    │   ├── flutter_release-1.0.aar      ← 主 aar
    │   └── flutter_release-1.0.pom      ← 依赖声明
    └── flutter_release_2.x.x/           ← 插件 aar（自动传递依赖）
```

#### 优缺点

| 维度 | 评价 |
|------|------|
| 开发效率 | ⭐⭐ 改动需要发版，联调麻烦 |
| 编译速度 | ⭐⭐⭐⭐⭐ 快，直接用 aar |
| Flutter 环境要求 | 原生团队不需要，只有 Flutter 团队需要 |
| 团队协作 | ⭐⭐⭐⭐⭐ 解耦，各管各的仓库 |
| 适用场景 | 多仓模式、正式发版、原生团队独立开发 |

## 三、面试标准答案（直接背）

### 基础版（1 分钟）

> "我们用的是**多仓 + aar 产物依赖**的方式。Flutter 业务模块是独立仓库，
> 打完 aar 发布到公司 maven 仓库，原生工程通过版本号依赖。
>
> 这样原生团队不需要搭 Flutter 环境，编译也快，版本管理也清晰。
> 开发调试阶段我们 Flutter 同学会用源码依赖的方式，改完代码直接跑。"

### 进阶版（3 分钟，体现深度）

> "我们 Flutter 和原生的集成分两种场景：
>
> **第一种是多仓模式下的 aar 产物依赖**，这是正式方案。
> Flutter 模块是独立的 Git 仓库，通过 `flutter build aar` 打 aar 产物，
> 发布到公司的 maven 仓库，原生工程像依赖普通第三方库一样依赖 Flutter 模块，
> 通过版本号管理升级。这样做的好处是团队解耦，原生团队不需要 Flutter 环境，
> 编译速度也快。
>
> **第二种是源码依赖**，用于开发调试阶段。
> 通过 `include_flutter.groovy` 脚本把 Flutter 模块注册为 Gradle 子项目，
> 原生工程 `implementation project(':flutter')`。
> 这样改完 Flutter 代码直接运行，立即可见，调试效率高。
>
> 我个人觉得两种方式各有适用场景，大团队用 aar 产物更规范，
> 小团队用源码依赖效率更高。我们团队因为有独立的 Android 和 iOS 团队，
> 所以用的是多仓 + aar 的方式。
>
> 在这个过程中我也踩过一些坑，比如 AGP 版本兼容问题、
> Flutter 插件的传递依赖处理、混淆配置等等……"

（然后面试官大概率会追问具体坑，你就可以顺着讲了）

## 四、常见追问及答案

### Q1：include_flutter.groovy 做了什么？

> "这个脚本是 Flutter 官方提供的，主要做三件事：
> 1. 把 Flutter Module 的 `.android/Flutter` 目录注册为 `:flutter` 子项目，
>    这是一个标准的 Android Library，应用了 Flutter Gradle 插件
> 2. 扫描所有 Flutter 插件，把每个插件的 Android 代码也注册为子项目
> 3. 加载 Flutter SDK 的 Gradle 插件和构建环境
>
> 这样原生工程就可以像依赖普通 library 一样依赖 Flutter 模块了。"

### Q2：Flutter 插件怎么处理？

> "Flutter 插件同时有 Dart 端和原生端的代码。
> 用源码依赖时，`include_flutter.groovy` 会自动把所有插件的
> Android 代码注册为 Gradle 子项目，主工程自动依赖。
>
> 用 aar 依赖时，每个插件也会生成自己的 aar，
> 主 aar 的 pom 文件里声明了对插件 aar 的依赖，
> 所以原生只需要依赖主 aar，插件 aar 会自动传递依赖进来。"

### Q3：为什么不用源码依赖，要搞 aar 这么麻烦？

> "主要是团队协作和效率的考量：
> 1. **团队解耦**：原生团队和 Flutter 团队是两个团队，各有各的仓库和发版节奏
> 2. **编译速度**：原生团队每次编译不需要等 Flutter 编译，速度快很多
> 3. **环境要求**：原生同学不需要搭 Flutter 环境，降低门槛
> 4. **版本管理**：通过版本号管理升级，出问题也方便回滚
>
> 当然代价就是联调麻烦一点，所以我们 Flutter 同学自己开发时还是用源码依赖，
> 提测和发版才走 aar 流程。"

### Q4：dependencies 里为什么是 `:flutter` 而不是 `:flutter_ecom`？

> "这个名字是 `include_flutter.groovy` 脚本里硬编码的，
> 不管你的 Flutter Module 叫什么名字，注册出来的子项目都叫 `:flutter`。
> 脚本里有一行 `gradle.include ":flutter"`，然后把 projectDir 指向
> 你的 Flutter Module 的 `.android/Flutter` 目录。
>
> 所以即使有多个 Flutter Module，也不能同时源码依赖两个，
> 因为名字冲突了。这也是多 Flutter 模块场景下一般用 aar 依赖的原因之一。"

### Q5：release 包混淆要注意什么？

> "主要是要保留 Flutter 相关的类不被混淆掉，不然会白屏或者 crash。
> 一般要在 proguard-rules.pro 里加：
> ```
> -keep class io.flutter.app.** { *; }
> -keep class io.flutter.plugin.** { *; }
> -keep class io.flutter.util.** { *; }
> -keep class io.flutter.view.** { *; }
> -keep class io.flutter.** { *; }
> ```
> 另外自己通过 MethodChannel 调用的原生类也要注意保留，
> 不然混淆后类名变了，Channel 调用会找不到方法。"

### Q6：Flutter 包体积有多大？怎么优化？

> "Flutter 引擎本身有一定体积，大概 armeabi-v7a 是 4-5MB，arm64-v8a 是 5-6MB。
> 再加上业务代码和资源，一般增加 10-20MB 左右。
>
> 优化手段包括：
> 1. 按 ABI 拆分 apk，用户只下载对应架构的 so
> 2. 资源压缩，用 webp 格式图片
> 3. 用 --split-debug-info 去掉调试符号
> 4. 合理使用懒加载，减少首屏资源
> 5. 去除未使用的插件和依赖"

## 五、回答技巧

1. **先说结论，再展开** — 先讲"我们用的是多仓 + aar 方式"，再讲为什么
2. **两种都提** — 展示你不是只会一种，而是知道多种方案的取舍
3. **结合项目说** — "我们团队因为 xxx 所以选了 xxx"，显得真实
4. **主动引导** — 说完可以加"过程中也踩过一些坑"，引导面试官追问你准备好的内容
5. **别瞎编** — 不确定的就说"这块我了解的是 xxx，具体还要再确认一下"
